## 为什么需要 Secrets

CI 常常要「身份凭证」才能干活：推送到别的仓库、调 Vercel / npm / Docker 的 API、访问测试数据库。这些字符串**一旦 commit 进仓库就等于公开**——哪怕是私有仓库，也应视为泄漏。

GitHub 的答案：**Secrets（加密存储的变量）**。你在仓库设置里存一次，workflow 里按名字引用，日志会自动打码。

## 存哪、怎么用

存储路径：仓库 **Settings → Secrets and variables → Actions → New repository secret**，比如建一个 `VERCEL_TOKEN`。

在 YAML 里用 `${{ secrets.名字 }}` 引用：

```yaml
- uses: actions/setup-node@v5
  with:
    node-version: 22
- run: npm ci
- run: npx vercel deploy --prod --token ${{ secrets.VERCEL_TOKEN }}
```

<Callout type="warn">
**三个铁律：**
① 名字区分大小写，`secrets.token` 引用不到 `VERCEL_TOKEN`。
② 别把 secret 直接 `echo` 出来——虽然日志会打码，但打码不代表安全。
③ fork 来的 PR **默认拿不到**你仓库的 secrets（防外人偷密钥），这是特性不是 bug。
</Callout>

## Environments：给部署上锁

**Environment** 是在 secrets 之上加一层的「部署环境」概念（如 `staging`、`production`）。价值：

- **环境级 secrets**：同一个 `DATABASE_URL`，production 和 staging 各存一份值。
- **人工审批（Required reviewers）**：部署到 production 前，指定的人点批准才继续——solo 用户也可以只批自己，相当于强制冷静一下。
- **环境 URL 与部署记录**：Release/PR 页面会显示环境链接。

在 Settings → Environments 创建，然后 job 上声明归属：

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production   # 引用该环境的 secrets 和审批规则
    steps:
      - run: echo "部署目标 ${{ vars.API_URL }}"
```

## vars 与 secrets 的区别

| | Secrets | Variables (vars) |
| --- | --- | --- |
| 引用 | `${{ secrets.NAME }}` | `${{ vars.NAME }}` |
| 性质 | 敏感，日志打码 | 非敏感配置，如 URL、账号 ID |
| 例子 | `VERCEL_TOKEN` | `VERCEL_PROJECT_ID` |

## 动手清单

1. 去你练手的仓库 Settings → Secrets and variables → Actions，建一个 `WHOAMI` secret 存你的名字。
2. 写个小 workflow：`- run: echo "hello ${{ secrets.WHOAMI }}"`，看日志里名字是否被打码。
3. 建一个 `staging` environment，加上 Required reviewer（填自己），体验 job 卡在等批准的样子。
4. 检查你所有仓库：**任何 token / 密码都不应出现在代码里**，已泄漏的立刻去源头吊销。
