## 为什么需要 Fork

给别人的开源项目提改动时，你**没有直接 push 分支的权限**。GitHub 的解法：把整个仓库**复制一份到你自己的账户**（这就叫 fork），在你这份上随便改，再请求合并回原仓库。

## 四方关系

```
上游 upstream:  original-owner/repo   ←── 你想贡献的目标
        ▲
        │  Pull Request（跨仓库）
        │
你的 fork:      yongkong/repo          ←── 你有全部权限的副本
```

- 你 clone 的是**自己的 fork**。
- 原仓库在 GitHub 术语里叫 **upstream（上游）**，你的叫 **fork（派生）**。

## 贡献五步

1. 目标仓库页点右上角 **Fork** → 得到 `yongkong/repo`。
2. clone 你的 fork，本地改代码、commit。
3. push 回你的 fork 的一个新分支。
4. GitHub 会提示 **Contribute → Open pull request**（注意：PR 从你的 fork → 上游）。
5. 上游维护者 review、要求修改或合并。

## 保持与上游同步（最坑的一步）

你 fork 之后，上游一直在变。长期不同步，你的 PR 会越来越难合。做法：给你的本地仓库加一个指向 upstream 的 remote，定期把上游 main 拉进来。

```bash
# 一次性：添加上游
git remote add upstream https://github.com/original-owner/repo.git

# 每次开工前：把上游最新拉下来
git fetch upstream
git switch main
git merge upstream/main   # 或 git rebase upstream/main
git push                  # 更新你自己的 fork
```

<Callout type="warn">
GitHub 网页上 fork 若落后上游，会显示 **"This branch is behind ..."** 和一个 **Sync fork** 按钮——轻量同步可用它，但复杂项目建议用上面的命令行方式掌控。
</Callout>

## 动手清单

1. 找一个小而友好的开源仓库（有 `good first issue` 标签的），点 **Fork**。
2. clone 你的 fork，加一个 upstream remote（照上面命令）。
3. 不改代码，只跑一次 `git fetch upstream` + `git merge upstream/main`，练习同步。
4. 挑一个 `good first issue`，将来学完 PR/review 后回来真正提一个 PR。
