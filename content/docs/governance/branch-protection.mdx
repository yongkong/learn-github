## 为什么 solo 开发者也需要它

你前面已经会了 CI 和自动部署。但如果任何人（包括手滑的你）都能 `git push --force` 覆盖 main、或者顶着红 CI 直接 merge，那前面所有质量投资都白搭。**分支保护（branch protection）** 就是给分支上规则：不符合条件的合并，GitHub 直接拒绝按钮。

路径：仓库 **Settings → Branches → Add branch protection rule**，对 `main` 生效。

## 值得立刻开的五个开关

| 规则 | 挡住的事故 |
| --- | --- |
| ☑ Require a pull request before merging | 直接 push 到 main 绕过 review |
| ☑ Require status checks to pass | 顶着红 CI 合并（勾上你的 `test` job） |
| ☑ Require branches to be up to date before merging | 合并后才发现在旧代码上测试过 |
| ☑ Do not allow force pushes | `--force` 抹掉主干历史 |
| ☑ Require linear history（可选） | 乱七八糟的 merge 提交交织 |

<Callout type="info">
**solo 起步配置**：前两条 + 禁 force push 就够——它挡的不是同事，是未来的自己和「手比脑子快」的瞬间。团队化后再加 review 人数要求。
</Callout>

## Required Reviewers 与 CODEOWNERS

- **Require reviews from code owners**：涉及某人负责的文件，必须由他批准。
- 搭配下一节课的 `CODEOWNERS` 文件使用，评审人自动被 @ 进来，不用满世界找人。

## Branch Rulesets：新一代做法

GitHub 正在用 **Rulesets**（Settings → Rules → Rulesets）取代老的 branch protection：规则可复用、可应用到多个分支/仓库、本地也能用 `git push --dry-run` 预检。新仓库建议直接从 Rulesets 开始；概念与上表一一对应。

## 动手清单

1. 打开你练手仓库的 Settings → Branches，给 `main` 建一条保护规则。
2. 勾上 Require PR + Require status checks（选你 CI 的 job 名）。
3. 亲手当一次坏人：本地直接向 main 强推、或建一个红 CI 的 PR 试着 merge，看 GitHub 怎么拒绝你。
4. 如果这是团队仓库（或未来的），把「谁负责哪块」用下一课的 CODEOWNERS 固化下来。
